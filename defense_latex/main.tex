\chapter{Experimental Evaluation}

Spara (\texttt{gsplit}) is an efficient distributed GNN training system built on top
of the Deep Graph Library (DGL). It introduces \emph{partition-aware sampling} and
\emph{feature loading} to reduce cross-GPU communication during multi-GPU GNN
training: each GPU owns a METIS partition (weighted by sampling frequency), and
sampling, feature caching, and the model forward/backward exchange only boundary data
across GPUs via NCCL. We are additionally exploring \emph{hybrid parallelism}: for
certain hidden sizes and depths the split communication cost becomes too large, and a
hybrid of data- and split-parallelism should do better. To choose the best strategy
\emph{without} building every variant, we use a cost-model simulator; this chapter
reports the measured system performance (Section~\ref{sec:measured}) and how faithfully
the simulator reproduces it (Section~\ref{sec:simulator}).

\paragraph{Setup.}
All experiments ran on \textbf{RunPod}, on a node with \textbf{2$\times$ NVIDIA
A100-SXM4-80GB} GPUs (NVLink/NVSwitch). Software: \textbf{CUDA 12.4},
\textbf{PyTorch 2.4 (cu124)}, and a custom \textbf{DGL} build with the Spara
C++/CUDA operators. We run the \texttt{split} (Spara) system on OGB
node-classification graphs with \textbf{fanout 15 per layer}, hidden size 256, batch
size 1024, real OGB features, on \textbf{2 GPUs} (\texttt{world\_size}$=2$, 2-partition
map \texttt{\_w2\_ndst\_efreq\_xbal}, UVA mode), sweeping depth over $\{3,4,5\}$ and
models \{GraphSAGE, GAT\}. All times are per-epoch averages.

\paragraph{Where the bottleneck is (and isn't).}
Neighbor sampling is \emph{not} the primary target for parallelism: the local sampling
work depends only on topology and fanout, is \textbf{independent of hidden size}, and
across our runs is relatively insensitive to depth. It is also
\emph{strategy-independent}---incurred identically under data, split, or hybrid
parallelism---so changing the parallelism strategy cannot reduce it. (In the
\texttt{split} measurements the ``Sample'' column additionally bundles the
partition-aware neighbor exchange over NCCL, i.e.\ communication, which is why it is
large.) The costs that actually drive the parallelism trade-off are \textbf{feature
loading} and \textbf{cross-partition communication}, which grow with hidden size and
depth---these are what the simulator models and what hybrid parallelism aims to reduce.
On papers100M the load cost jumps at depth~5 as the working set exceeds the on-GPU
feature cache and more features are gathered from host memory over UVA; and GAT's
heavier per-layer compute roughly doubles train time vs.\ SAGE at equal depth.

\section{Simulator Fidelity}
\label{sec:simulator}

To pick a hybrid-parallelism strategy before building it, Spara includes a cost-model
simulator (\texttt{get\_best\_strategy.py} $\rightarrow$
\texttt{simulation/hybrid\_dp\_sim.py}). For a given graph, model, depth and hidden
size it sweeps the \emph{split-point} $k$ (the layer from which split parallelism is
used): $k=0$ is full split parallelism---identical to the measured \texttt{split}
system---and $k=L$ is full data parallelism. For each $k$ it predicts the per-epoch
\textbf{computation} cost (model-layer compute, timed on GPU), \textbf{communication}
cost (cross-partition feature volume $\div$ interconnect bandwidth), and
\textbf{data-loading} cost (frontier feature transfer $\div$ PCIe). The simulator writes
results through the same logging path as the measured runs, so the two are directly
comparable.

We compare the simulator's $k{=}0$ prediction against the measured numbers from
Section~\ref{sec:measured}. The compute-cost model times the \emph{forward} pass only,
so the honest comparison is predicted \emph{computation} vs.\ measured \emph{forward}
(a full training step adds a backward pass of comparable cost). Predicted
\emph{data-loading} is compared to measured \emph{load}; sampling is deliberately not
modelled (Section~\ref{sec:measured}).

\paragraph{Findings.}
The \textbf{compute model is accurate}: on products it tracks the measured forward
time within $\sim$10--25\% (e.g.\ SAGE depth~4: $4.77$ vs.\ $4.73$\,s), confirming the
GPU layer-timing approach is sound; it under-predicts on the tiny arxiv graph where
fixed kernel-launch overhead dominates. The \textbf{data-loading model is the main
source of error}: it over-predicts by $30$--$150\times$ because it assumes \emph{every}
frontier feature is transferred over PCIe and \textbf{ignores the on-GPU feature
cache}---with a $10$\,GB cache, products' features are resident and the measured load is
near zero. Predicted \textbf{communication} is small, consistent with the NVLink fabric.

\paragraph{Simple improvements (not yet applied).}
\begin{enumerate}
  \item \textbf{Add the backward pass} to the compute cost (currently forward-only);
        a full step is $\approx 2\times$ forward, so either double the estimate or time
        the backward explicitly.
  \item \textbf{Model the feature cache} in the data-loading cost: subtract the
        \texttt{cache\_size}-resident (partition-local) nodes and only charge PCIe for
        the uncached remainder. This is the single biggest fix.
  \item \textbf{Fix the hop$\rightarrow$layer mapping} (\texttt{model\_layers[-layer\_no]}),
        which likely explains the arxiv/GAT under-prediction at deeper layers.
  \item \textbf{Average over a few epochs} for small graphs to remove launch-overhead noise.
  \item \textbf{Confirm the interconnect branch} matches the A100-SXM NVLink topology.
\end{enumerate}

\paragraph{Reduced-hidden-size projection (feasibility --- to be proven first).}
A promising shortcut is to measure cost at a \emph{small} hidden size and project to
larger ones, avoiding a full sweep. The components scale differently:
\emph{communication} and \emph{data-loading} are $\propto$ (boundary nodes $\times$
hidden), i.e.\ \textbf{linear} in hidden size and projectable by a single scale factor;
\emph{computation} contains the hidden$\rightarrow$hidden GEMMs, which are
$\propto \text{hidden}^2$, so it is \textbf{affine--quadratic}, $a\,h + b\,h^2$, not a
single linear factor. Before relying on this, we must \emph{prove} projectability:
measure each phase at a few hidden sizes (e.g.\ $64,128,256,512$) at fixed
graph/depth, fit linear vs.\ quadratic forms, and report the residual/error of
projecting small$\rightarrow$large. This is left as the next step.

\section{Microprofile Validation (nsys)}
\label{sec:microprofile}
To verify the cost model independently we microprofiled, on one representative
batch, the \emph{fused} full-model forward$+$backward (what the trainer runs) against
the simulator's \emph{per-layer isolated} forward$+$backward, swept over hidden size
and model, with an \texttt{nsys} cross-check; and we measured the real pinned-host
$\rightarrow$GPU feature gather over feature size.

\paragraph{Findings.}
(1) \textbf{Interconnect/bandwidth is now calibrated to hardware}: NVLink is
$300$\,GB/s (confirmed via \texttt{nvidia-smi topo}: GPU0--GPU1 are NV12, i.e.\
$12\times25$\,GB/s), and the pinned-host$\rightarrow$GPU gather sustains a steady
\textbf{$\sim$25--26\,GB/s} independent of feature size, so \texttt{PCIE\_BW} was
corrected $16\rightarrow25$\,GB/s.
(2) \textbf{Feature loading is linear in feature size} (gather time $9.0\rightarrow139$\,ms
as features go $64\rightarrow1024$; $\sim$constant GB/s), so the load/communication
terms project cleanly by a single scale factor in feature (and hidden) size.
(3) \textbf{Compute is GPU-bound GEMM} (\texttt{nsys}: \texttt{ampere\_sgemm\_*} kernels
dominate), confirming the timing is real.
(4) \textbf{The compute cost model originally over-counted} the fused step by
$1.5\text{--}3.5\times$, worsening with hidden size, because it paired sampled hop $j$
(seeds-outward) with convolution $\text{-}j$ instead of $L\!-\!1\!-\!j$---placing the
expensive hidden$\times$hidden GEMMs on the largest outer frontiers. \textbf{After
correcting the hop$\rightarrow$layer pairing} (and dropping the input gradient on the
true input layer), the summed per-layer estimate matches the fused full-model step to
\textbf{within $\sim$2--5\% for SAGE at hidden $\ge 256$} (Table~\ref{tab:micro-compute})
---i.e.\ in the large-hidden regime where communication dominates and the hybrid
decision actually matters. The residual ($\sim$1.4$\times$ at small hidden, higher for
GAT) is the \emph{inherent per-layer overhead} of a per-layer cost model: isolated
backward setup and kernel-launch/attention small-ops that the fused step amortizes, and
which are a large fraction only when the GEMM itself is tiny. Per-layer attribution is
kept deliberately, to extend to pipeline and hybrid data parallelism. Data-loading and
interconnect are validated (Findings 1--3).
